# T003｜两项经研究者批准的特化不足（2026-10-22）

> 必须绑定 [T003 两项已审特色](ARCHITECTURE.md)，不是泛泛地讲“RL 有噪声”“多 Agent 可能相互影响”。这里**区分论文明确采用的设计**与**我们尚未实证的风险推论**。

## ① TD008 ↔ 拆分 LLM 调用后，奖励仍未准确分配各步贡献

- **绑定的机制**：[TD008](../../knowledge/deltas/TD008_agent_call_transition_lightningrl.md)：将多轮 Agent 的每次 LLM 决策拆成独立 `(input, output, reward)`，交给单轮 RL 优化参数。
- **独有缺口**：同一次任务里“第一次生成错误 SQL→第二次发现错误→第三次修复成功”，**2025 原论文的简单 LightningRL 策略给可训练的各次 LLM 调用同一终端回报 R**，不在调用之间区分谁导致错误、谁完成修复。之后仍由单轮 RL 算法计算各 token 的学习信号，不能误称为“所有 token 梯度完全一样”。
- **证据身份**：原论文 §3.3.2 明示当前的简单分配方式；§5.2 讨论更细的 credit assignment。**“坏的中间行为会因此得到错误强化并降低最终性能”是可能机制，不是作者已独立证实的实际故障。**
- **针对性验证**：在相同 Agent、任务、模型和 RL 预算下，与**相同终端 R**对照：利用环境有效性、修复必要性、工具错误等生成的**调用级回报/优势差异**，检查中间步骤质量和最终任务成功率；勿只比较两条不同框架的最终成绩。

## ② TD009 ↔ 按角色筛选训练样本，但共享模型与角色依赖不自动隔离

- **绑定的机制**：[TD009](../../knowledge/deltas/TD009_role_selected_agent_training.md)：从 Agent 轨迹中选择 Writer/Rewriter 等特定角色的调用训练模型，Checker 等其他角色不直接提供训练样本。
- **独有缺口**：原文 §4.1 的 SQL 角色可以共用同一基础 LLM，不同 Prompt 扮演不同职责。训练所选调用后**共享权重 `θ` 改变**，因此未选中 Checker 之后的表现并非天然不变。对于不同模型的多角色系统，分别优化也可能忽略彼此的工作依赖关系。
- **证据身份**：原文 §3.2.2、§4.1 支持结构/实验设置；**“Checker 表现实际下降”没有被论文证实**，也不能从“训练样本没包含 Checker”推断其能力一定没变化。
- **针对性验证**：同时记录 Writer、Rewriter、Checker 在训练前后的独立正确率/改写质量及整个 Agent 结果；比较共享权重、分离模型/适配器、不同角色训练选择，或检查不同角色交互中的变化。这是待检验问题，**不构成已经批准的系统实施方案**。

**本轮审批/边界**：研究者于 2026-10-22 批准上述两项特色和两项对应不足；对应 [TD008](../../knowledge/deltas/TD008_agent_call_transition_lightningrl.md) / [TD009](../../knowledge/deltas/TD009_role_selected_agent_training.md)。来源为 [2025 原论文](https://arxiv.org/html/2508.03680) §3.2–3.3、§4.1、§5.2，与 2026 Agent Lightning v1.0 不混写；未独立复现。
