## 2. 双库与六类记录（概念结构已认可）

**逻辑两库、统一查询入口**：可以使用一套持久化存储；不等于必须运行两个物理数据库，也**没有拍板 SQLite/向量数据库等具体技术**。

| 逻辑类型 | 归属 | 内容 |
|---|---|---|
| ① **Source** | **先验**；也可记录内部实验的产物来源 | 论文/研报/GitHub 等的身份、公开来源、原始文件或 PDF 版本、核验状态 |
| ② **Knowledge** | **C 先验** | 客观金融现象、显式统计量/公式、聚合路径、模型方法（FIN / ARCH 需区分） |
| ③ **Claim** | **C 先验** | 作者自己的假设、解释、实验观察、正负结果及条件，不当作我们已复现 |
| ④ **Factor** | **先验与经验均有** | 作者提出的因子定义，或 Agent 自己生成的代码/公式与父代 |
| ⑤ **Experiment** | **先验与经验均有** | 作者**报告**的实验（external_reported），或我们**实际运行**的实验（internal_executed） |
| ⑥ **Relation** | **共用关联层，尤其用于经验** | 来源→知识/结论，知识→因子，父因子→子因子，因子→多次实验等可核实连接 |

**共同检索外壳（原则认可，物理字段尚可简化）**：\`id\`、\`type\`、\`name\`、\`description\`、\`tags\`、\`required_data\`、\`time_info\`（频率、输出粒度、信息可见时间）、\`source_refs\`。两库**只统一检索接口与基本元数据**，而不强迫所有内容字段一样。

**各类专属内容（设计方向而非已冻结 SQL Schema）**：
- Knowledge：\`definition/calculation\`、输出对象、方法依赖、是否有完整原文公式；ARCH 模型不能硬扭成可解释金融 Alpha。
- Claim：\`claim_type\`、\`statement\`、市场/样本/预测窗口、作者报告结果、正负证据、原文位置和核验状态。**Evidence 可保留，但不能成为“应优先生成这个因子”的指令。**
- Factor：表达式、实际代码版本、父代、生成背景、真实使用的知识引用、数据需求；**不能凭事后相似性伪称使用某篇论文**。
- Experiment：因子 ID、数据和时间切分、评测版本/配置、执行/检查状态、Returns/Sharpe/MDD/Turnover/Score、失败原因、结果与日志路径；**同一因子可以被测试多次**，运行失败与预测效果差不能混成一个布尔 \`success\`。
- Relation：保留关系类型和可靠来源，能从经验追溯到 C 知识、父代和实验配置。

**明确避免的错误**：
1. **不因我们的回测失败就自动修改/降权原始 C 知识**；修正 C 的定义仅依据新的原文核验。成功/失败经验在 Experience 中追加，并经关联呈现。
2. 论文作者报告的收益/IC 不是我们的实测 Score；必须保留 \`external_reported\` vs \`internal_executed\` 身份。
3. 不强制为所有资料生成可执行公式。比如 C001 有可核 RSJ 定义；CR002 只可核摘要、关键公式缺失；C008N 主要是模型结构和预测实验，不应造出显式金融因子。
4. 不把历史高分因子自动写成“金融先验有效性权重”，也不要求 V1 立刻设计自适应知识权重。

## 3. 统一查询为什么难（讨论中尚未解决的关键问题）

研究者明确不认可“用 tags 匹配几篇文章 → 按固定相似度返回 Top-K → 一股脑塞进生成 Prompt”作为唯一方案。原因：
- **Tags 不够**：如动量、反转、日内时点/时间结构、成交量、条件聚合等，可跨标签产生新联系；只看标签会丢掉未预设的语义关系。
- **纯相似度 Top-K 太固定**：同样的研究任务在不同轮次总得到相似来源，容易造成生成同质化。
- **只依赖数据库反而限制创新**：用户在 Codex 实际任务中遇到过“先读知识库，再生成”导致构思受困的情况；“先独立想，再检索去重”是需要保留的有效使用经验。
- **不能全量阅读**：所有先验及全部经验不断增长；将全文或全部研究档案拼到每轮 Prompt 既不可扩展，也不利于信息质量。
- **需要随机性但非无意义噪声**：用户明确举例，研究动量时希望**有机会接触反转或时间结构等非直接匹配知识**，以产生新联系；并非随机抽任何文件都合理。
- **检索输出给谁、何时给**：先生成假设再查？先检索后构思？分几轮展开？工具把知识卡作为返回值、由调用 Agent 消化，还是直接注入 Prompt？这决定 Agent 的自由度。

**尚未采纳的候选思路（只是讨论建议）**：
- 自由构思 → 查先验/经验去重与核对；
- 知识启发 → 查相关金融知识再自主联想；
- 跨主题探索 → 受控抽取距离稍远但可能有联系的来源；
- 混合检索（元数据/全文/语义）+ 去重与多样性 + 少量随机性；一次查询分别展示 C 知识和对应经验；需要时才展开原文。
这些路径**不能视作已定的三路调度器**，具体路径数、频率、配比、采样算法、模型参数及 API 都还没定。

## 4. 本轮最新提出的替代方案：LLM + Prompt + API 检索工具（首要待决）

**研究者的提议**：已有多个可接入的模型 API，不必默认传统 RAG。能否写一组专用 Prompt，直接由一个**智能检索 Agent/Tool**理解任务、规划查找、探索相关或跨领域知识、选取有用条目，再把结构化结果交给 Research Agent？这可能更灵活、接口更方便，并允许模型做复杂语义关联。

**要在新对话中比较，而不是立即选择**：

| 路线 | 潜在优势 | 必须回答的风险/条件 |
|---|---|---|
| 传统规则/全文/向量检索（常称 RAG 的检索部分） | 快、可扩展、可重现、便于按字段过滤 | 固定相似度排序可能同质化；缺跨主题推理 |
| **LLM + Prompt 驱动检索 Agent** | 能理解复杂意图、重写查询、探索相邻或反向机制、动态组织返回内容 | **LLM 看不到未提供/未检索的全部库内容**；若每轮逐篇阅读成本高且结果不稳定；权限和精度也要控制 |
| **混合方案** | LLM 负责查询规划与语义扩展，结构化/全文/向量索引负责高覆盖召回，工具负责可追溯输出 | 多了一层组织复杂度；需防止检索 Agent 变成替生成 Agent 先作因子决策的角色 |

**必要提醒**：RAG 通常是“检索外部信息、再提供给模型”的整体模式，不必只等同向量 Top-K。LLM 驱动查询工具也可能在内部使用检索索引，因此二者不是互斥选项。**用户并未确定优选路线**；不要将上表第三行直接写成结论。

需要在新对话中澄清具体的输入输出契约：
1. Research Agent 如何表达查询需求，以及自由探索是否可以**完全不事先检索**；
2. 检索服务如何访问完整 C/经验索引（而非让 LLM 凭已有上下文猜存了什么）；
3. 怎样平衡相关性、跨域、多样性与可控随机性，并避免常见来源反复占据前列；
4. 一次返回哪些字段，如何对作者结果/自测结果分别标注来源；什么时候展开详细公式和原文；
5. 怎样保持独立构思，避免检索内容预先限制生成空间；怎样记录查询和采样以便重现。

## 5. 已确定的 Evaluator V1（不要在新对话中重新选参数）

评测详情的**唯一权威入口**：[单因子多空组合评分标准 V1](../../evaluation/PORTFOLIO_SCORING_STANDARD.md)。

\[
Score_{V1}=1.0R_{\mathrm{ann,gross}}+0.05SR_{\mathrm{gross}}
-0.1MDD_{\mathrm{gross}}-C_{\mathrm{ann}}
\]

- 每天横截面 **1%/99% Winsorization**，随后去均值并按绝对值和归一化；理论多头 +0.5、空头 -0.5，日频更新目标权重。
- 信号 \`t\` 与随后理论 VWAP 收益须按时点对齐（目标为次日 VWAP 入、再下一交易日 VWAP 出的**一期**收益，不是持有两天）。
- 近似双边日换手 \`TO_t = Σ_i |w[t,i]-w[t-1,i]|\`；统一**每单位交易额 10 bps**：\`Cost_t = 0.001×TO_t\`，\`C_ann = 252×mean(Cost_t)\`。
- Returns、Sharpe、MDD 从**毛收益**计算，交易成本在 Objective **单独扣一次**，不双重扣费。系数 1、0.05、−0.1 是研究讨论先采用的 V1 基准，**非学界公认最优**。
- **单因子 Score ≠ P005 因子池边际贡献** \`ΔΓ\`：前者评单个因子组合表现，后者评加入现有池的增益；当前只确认二者应分开记录，未在这一轮重新设计二者关系或池级选拔规则。
- 股票池、停牌、真实撮合等更细工程边界不在此次讨论范围；不存在已跑通回测的主张。

## 7. 下一段对话的建议起点（问题，不是批准的方案）

从一个问题开始：

> **我们的 Retrieval Agent 到底应该做什么？** 是负责“找出符合条件的知识和经验”，还是还要负责“重写研究问题、寻找反向/远缘联系、决定给生成 Agent 哪些材料”？哪些由独立 LLM API 调用承担，哪些留给程序化索引，哪些严格保留给 Research Generator 自己决策？

先明确检索 Agent 的职责边界和“先想再查”的时机，再确定字段查询、Prompt、随机策略和具体技术选型。**不要在没有这一步讨论时，直接实现一个固定的 RAG 管线或让检索工具接管因子生成。**
