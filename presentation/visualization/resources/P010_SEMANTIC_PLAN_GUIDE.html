1. “金融语义词表”不是一张行情表，也不是 140 个因子

所谓语义条目，可以当作研究假设的“积木块”。每一块记录一个金融含义，而不是一条可以直接运行的因子公式。

类型回答什么问题通俗举例
Event（事件）价格或量能发生了什么？突破价格区间、放量、波动收缩
Context（情境）在什么位置或市场背景下发生？近期高点附近、VWAP 附近
Qualities（确认与过滤）需要哪些额外确认或剔除条件？成交量确认、冷却重复信号
Direction（预期方向）这件事暗示之后怎么走？趋势延续、反转、区间震荡
Output（输出方式）最后给股票一个什么信号？连续分数、截面排名、事件衰减

这些积木通常存成 JSON 文件。每个条目有 schema_id、类别、名称、语义描述、术语定义、scope（时序或截面），没有强制指定 Python 运算符、20 日还是 60 日窗口、买卖阈值；那些留给后续实现 Agent。

词表从哪来？ 原文 Appendix C 说可从卖方研报、金融论文、书籍、研究经验和研究目标抽取机制，再去掉具体公式、标注类别、查重后形成记录。研究期间在线搜索只拿当前启用的条目排列组合；在不同搜索周期之间可以人工/离线更新词表，加入词表外的新经济机制，并非天生永久固定。它不是每天自动下载行情后生出 140 个新条目。

主论文实验用 140 个积木：Event 40、Context 40、Qualities 50、Direction 3、Output 7；当前 GitHub 默认分支的 schemas/stock_alpha/ 已扩展到167 个启用条目（Event54/Context43/Quality59/Direction3/Output8）。两者是不同版本口径，不能把当前文件数硬套为论文实验配置。

来源：论文 §3.1、Appendix C；当前公开 JSON 词表。

2. 五维 Plan 怎么从积木拼出来？它为什么不是代码？

系统从五个栏目取内容，形成一份结构化的研究计划 Plan=(Event,Context,Qualities,Direction,Output)，其中 Qualities 可以选 0–3 个，其余栏目一般各选 1 个。

这是根据论文 Appendix D 原始示例整理的中文简述：

Event       价量共同出现较强突破（在同日股票间比较）
Context     突破位置离该股 VWAP/均线参考点有多远
Quality     短时间内重复出现的同类事件要降权
Direction   延续：预期突破方向随后继续
Output      事件衰减：旧事件的信号随时间逐步减弱

这份 Plan 可以被理解成：“寻找出现较强价量突破、参考相对位置且排除近期重复噪声的股票，并把突破后的延续预期做成会随时间衰减的评分信号。”

注意：这里没有公式。 同一 Plan 交给不同 LLM，或者同一个 LLM 不同实现，都可能得到不同 Python 运算符、窗口、阈值；它们研究的金融含义却来自同一份 Plan。对应源码 Plan 是五个字段的 Python dataclass，并用条目 ID 组成 plan.key 方便查重。

五维语义 Plan：要验证的金融假设→LLM Code Agent 看到展开后的 JSON 描述
LLM Code Agent 看到展开后的 JSON 描述→生成可计算 Python 因子
生成可计算 Python 因子→真实历史市场数据运行与评价

3. “大量五维 Plan”从哪里冒出来？总数为什么会这么大？

不用叫 LLM 随便发明几千个想法。程序从词表里组合取样：例如选 1 个 Event、1 个 Context、选 0–3 个 Quality、1 个 Direction 和 1 个 Output。

计算一下“组合空间”数量，而不是实际评测次数： 主论文词表下，若把 Quality 集合看作不计顺序且互不重复，则可组成的理论组合数是：

40 个 Event × 40 个 Context × (C(50,0)+C(50,1)+C(50,2)+C(50,3))
× 3 个 Direction × 7 个 Output

= 约 7.01 亿种理论组合

并不是作者真的让 LLM 生成并运行了 7 亿次因子！论文每轮先抽取 10,000 个候选 Plan，筛掉已评过或重复的，再从里面决定哪些值得使用昂贵的 LLM 实现预算；实际主实验是 80 轮、每轮评估 16 份 Plan，总计 1,280 份 Plan 尝试（不是 1,280 个保证有效的最终因子）。

源代码：从五类 ID 中抽取 Plan。

4. 搜索调度器究竟怎么选下一批？三条通道不是三种 LLM

每轮抽到 10,000 个待选 Plan→② Exploit：LightGBM 事先预测奖励，优先高分 Plan
① Explore：优先没人研究过的事件／情境组合→调度器为三类候选各分配名额
② Exploit：LightGBM 事先预测奖励，优先高分 Plan→调度器为三类候选各分配名额
③ Mutate：微调一个语义条目，提出附近的新 Plan→调度器为三类候选各分配名额
调度器为三类候选各分配名额→最终挑16份 Plan
最终挑16份 Plan→逐份调用 LLM、执行因子、真实评分
逐份调用 LLM、执行因子、真实评分→Plan–Reward 历史库
Plan–Reward 历史库→② Exploit：LightGBM 事先预测奖励，优先高分 Plan
Plan–Reward 历史库→历史已评过的高奖励 Plan

  • 探索 Explore：数以前测过多少类似 Event、Context 以及两者的搭配。越少被评过，新颖度越高。论文 Appendix A.4 使用三部分加权新颖度（60% 事件-情境组合、25% 事件单项、15% 情境单项）；不是让 LLM 自己说“我觉得这个新鲜”。
  • 利用 Exploit：把 Plan 的字段做成机器可读特征，让 LightGBM 奖励预测器根据过去经验估计 预测奖励，把高分者送给代码 Agent 验证。预测只是便宜的排序参考，不是已实现的真实收益。
  • 局部变异 Mutate：从真正测试过且奖励高的 Plan 出发，只改动一个语义组件，产生“近邻”研究计划。不是修改 Python 算子树。

名额怎样分配？ 论文主方法写的是冷启动时全探索，之后探索比例随已评样本增加按照平滑函数下降，余下预算分给“高预测分”和“局部变异”。但当前代码 configs/default_stock_search.json 用明确的分阶段配额表，比如下列真实公开配置：

5. 你说的“取一个预期”：预测奖励是怎样学出来的？

系统不会凭空“预计” Plan 的分数。它先实际试过一些 Plan，留下配对数据：

(Plan A 的五维条目，真正运行后奖励 0.12)
(Plan B 的五维条目，真正运行后奖励 0.04)
(Plan C 的五维条目，真正运行后奖励 0.18)
...

上面 0.12 等是教学数字，不是论文报告。

程序把 Plan 变成类似 event=突破、context=高位、event_context=突破+高位、quality_count=1 的特征，再让 LightGBM 学习什么语义组合过去往往得到较好的真实评价。之后面对还没写代码的 Plan，它先给一个 预测奖励，让系统尽量少浪费 LLM/回测预算。

当前 reward_model.py 更具体：采用 8 个带不同抽样子集的 LightGBM 回归器；predict() 把8次预测的平均值作为预期奖励，同时输出一个标准差作为分歧大小。它们是外部机器学习模型，不是生成因子的 LLM。

“Plan–Reward 经验”究竟存什么？

LLM 实现成 fast/slow 两个尺度的因子→真实执行检查
真实执行检查→历史数据：RankIC、RankICIR、时滞罚分通过
真实执行检查→奖励记 0修复后仍失败
历史数据：RankIC、RankICIR、时滞罚分→取两个尺度较优奖励
取两个尺度较优奖励→经验记录：(Plan, 实测奖励)
奖励记 0→经验记录：(Plan, 实测奖励)
经验记录：(Plan, 实测奖励)→重新训练 LightGBM 奖励预测器
重新训练 LightGBM 奖励预测器→给下轮未实现 Plan 打预测分

真实奖励并不是简单“赚了多少钱”。论文用三个部分：

真实奖励 = 10 × RankIC + 1 × RankICIR − 2 × 时滞敏感度
  • RankIC：因子给股票的排序和未来收益排序有多一致。
  • RankICIR：这种排序预测能力在不同时期有多稳定。
  • 时滞惩罚：如果把信号晚一天使用时 RankIC 降得很明显，就对“过于依赖即时性”的方案扣分。
  • 每份 Plan 分别实现 fast/slow 两个时间尺度，各计算奖励，最终使用两者中较高的值。代码检验失败允许修复一次；修不好记 0 奖励，但这并不证明金融假设理论上完全无效。

这个真实奖励进入累积缓存，下一轮用它重新训练奖励预测器。不会更新生成因子的 DeepSeek-V4-Flash LLM 权重。

6. “树变异”是什么？这一篇其实没有变异树

P010 正文称为 local semantic mutation（局部语义变异），并非搜索因子公式的 AST 子树互换，也不是 P004 的 MCTS 搜索树。

比如上面原始 Plan 的方向是 延续，只把它换成反转，其余 Event/Context/Quality/Output 不变，就得到一个有明确差别的新 Plan；之后仍然交给 LLM 写 Python，并在真实数据上测试。

只做一个语义局部编辑→换方向：延续 → 反转
只做一个语义局部编辑→换 Context：高位 → VWAP 附近
只做一个语义局部编辑→换/增加/删除一个 Quality
只做一个语义局部编辑→换 Event 或 Output
换方向：延续 → 反转→排除重复或已评过 Plan
换 Context：高位 → VWAP 附近→排除重复或已评过 Plan
换/增加/删除一个 Quality→排除重复或已评过 Plan
换 Event 或 Output→排除重复或已评过 Plan
排除重复或已评过 Plan→新子 Plan：等待 LLM 实现与真实评分

论文 Appendix A.4 写明有七类具体变异操作：替换 Quality、替换 Context、替换 Output、添加 Quality、删除 Quality、替换 Direction、替换 Event，概率分别是 22%、16%、16%、14%、12%、12%、8%。这些在当前 schema_space.py 中也能找到可执行的对应分支。

一处论文与代码应分开看：正文说局部变异候选再经过奖励预测模型排序；当前 selector.py 的 select_batch() 则优先把符合条件的变异子代按生成顺序收进名额，后面才附上预测分数和名次用于记录。因此不能直接说当前默认分支在变异候选入选前实施了与正文完全相同的奖励预测排序。尚未固定论文实验对应的具体代码版本。

7. 最后留下什么？与 P005、P004、P006 的关键区别

合格因子先按实测奖励高低排序，再过滤与已入选因子高度相关的候选（论文阈值为 |corr| < 0.7），筛成最终因子池。这里不是 P005 那种每加入一个因子就重新拟合整池组合、计算池分数边际差 ΔΓ 的过程。

最终因子池会输入另一个下游 LightGBM 预测模型，在 Qlib Top50/Drop5 策略上评价组合。牢记两种 LightGBM：

  • 语义奖励模型：输入五维 Plan 特征，预测“值得不值得花钱实现这个金融假设”。
  • 股票预测模型：输入已生成的因子数值，预测或排序“哪只股票未来可能表现好”。
