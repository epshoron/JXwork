T003 · METHOD IN CONTEXT

Agent Lightning

保留现有多工具 Agent 的执行程序，通过统一轨迹接口为每次 LLM 调用分配奖励，再执行真正的参数级 RL。

执行轨迹 → RL 权重优化对象可核查作者结果 ≠ 独立复现
T003
01 / EXECUTION LOOP

原文机制如何流动？

实线按运行顺序；虚线回到下一次探索。每个方框代表实际输入、动作或检查，不意味着所有步骤都是模型训练。

真正更新的对象：真正更新 LLM 模型参数 θ；不是把评价报告改写为新 System Prompt。
02 / CONCRETE EXAMPLE

用一个例子看懂

SQL Agent 先拟写 SQL，执行报错后修复，再提交答案。训练器把各次 LLM 写作/修复调用拆成可训练的 transition；工具执行结果是上下文，不直接当成模型生成 token。

03 / DISTINCTIVE MECHANISMS

三个关键实现位置

TD008 · 调用级接口

复杂多轮 Agent 的轨迹拆成每次 LLM 调用，使现有单轮 RL 算法可接入。

TD009 · 角色选择训练

同一基础 LLM 不同 Prompt 可担任多角色；只挑 writer/rewriter 等需要改进的调用参与训练。

训练/执行解耦

Client 运行原有 Agent；Server 调度、采集与训练，再经 API 提供更新后的模型。

04 / RELATIONSHIPS

与其他路线怎么区分？

与 T005 一样属于权重训练，但 T003 奖励来自外部任务的工具轨迹；T005 用当前模型兼任 Judge 生成偏好，再做 DPO。

05 / CLAIMS & LIMITS

效果与证据边界

作者报告：论文在 Text-to-SQL、RAG 多跳问答和数学工具调用的训练/测试奖励曲线上报告改进；不同任务的奖励不可直接合并排名。

不要扩大解释：2025 原论文最简把终局 R 分配给每次调用，未证明细粒度步骤因果归因；需区分后续 v1.0 工程仓库版本。
